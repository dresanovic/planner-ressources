# FS-015 Research Decisions

## 1. Existing stack and feature boundary

**Decision**: Implement FS-015 in the current FastAPI/SQLAlchemy backend and
React/Vite client, following the existing API, transaction, migration, and
Vitest/pytest patterns. Add no runtime dependency.

**Rationale**: The repository already provides revision identities and
lifecycle rules through FS-013, calendar occurrence references through FS-014,
explicit SQLAlchemy transactions, sequential Alembic migrations, and a
single-shell React application. Standard-library cryptography primitives are
sufficient for a random bearer token.

**Alternatives considered**:

- A separate lecturer-review application: rejected because it duplicates
  deployment, domain access, and styling for one small public surface.
- A generic collaboration framework: rejected because accounts, approvals,
  threads, and other collaboration modes are outside this slice.
- New auth, router, cryptography, or task-queue packages: rejected because none
  is required by the approved behavior.

## 2. Current schedule cardinality

**Decision**: Keep the repository's existing rule that each `DraftSession` and
`ExamSession` has one `lecturer_id`. Test cross-lecturer privacy with courses
that have multiple eligible lecturers and distinct assigned sessions.
Multi-lecturer assignment of one scheduled session is explicitly outside
FS-015.

**Rationale**: Supporting several assigned lecturers on one session would
change generation, conflict checks, manual editing, lifecycle snapshots,
restoration, calendar contracts, and fixtures. The requested slice is one
lecturer's assigned schedule, and the current scalar assignment already
satisfies that outcome.

**Alternatives considered**:

- Add teaching/exam session-to-lecturer join tables: rejected as a cross-cutting
  scheduling feature unrelated to accountless review.
- Duplicate a shared session once per lecturer: rejected because it creates
  false independent schedule records and ambiguous edits.

## 3. Token creation and persistence

**Decision**: Generate the raw secret with `secrets.token_urlsafe(32)` and store
only the hexadecimal SHA-256 digest under a unique index. Accept only the exact
URL-safe token shape before hashing. Return the raw token only from successful
issue or replacement.

**Rationale**: Thirty-two random bytes provide 256 bits of unpredictability.
Because the secret is high-entropy and generated by the server, a direct digest
lookup is secure and efficient. Losing the one-time value is safely handled by
replacement.

**Alternatives considered**:

- Signed tokens containing lecturer, revision, or expiry data: rejected because
  the secret must contain no readable scope and revocation still requires
  persisted state.
- Store the raw token or reversible encryption: rejected because database or
  routine inspection would expose an immediately usable credential.
- Password hashing: rejected because a slow password KDF does not materially
  improve brute-force resistance for a uniformly random 256-bit value.

## 4. Browser link and public API transport

**Decision**: The issue/replacement API returns the raw secret once, after the
non-secret record commits. The planner client constructs the copied URL as
`{window.location.origin}/lecturer-review/#/{secret}`. The trusted gateway
serves the public review shell only at `/lecturer-review/`, while protecting
planner page entry points. Client bootstrap detects that public path and exact
fragment shape before rendering any planner navigation, retains the secret
only in component memory, and removes the fragment with
`history.replaceState` before the first API request. Fixed public endpoints
receive the secret in `Authorization: Bearer <secret>`. Production public
requests use relative same-origin URLs with `credentials: "omit"`; production
`VITE_API_BASE_URL` remains empty so the browser cannot bypass the gateway.

**Rationale**: URI fragments are not sent in initial HTTP request lines or
referrers. A fixed public path lets the gateway distinguish the public review
shell from protected planner pages without adding React Router. Removing the
fragment avoids retaining the credential in browser history; reopening the
original manually delivered link still works until its server-side end
condition. Client construction avoids trusting request headers or adding a
backend public-origin setting.

**Alternatives considered**:

- Secret in a path or query parameter: rejected because it commonly enters
  server logs, browser history, analytics, and referrer surfaces.
- Cookie or browser storage: rejected because it broadens persistence and
  cross-request exposure.
- A root-only hash route: rejected because the gateway cannot distinguish an
  accountless request for `/` from a protected planner-page request; fragments
  never reach the gateway.
- A new React Router dependency: rejected because the application has only one
  public route and already uses controlled in-memory destinations.
- Backend-generated absolute URLs: rejected because the planner client can use
  its authoritative browser origin and avoid another deployment setting.

## 5. Public response hardening

**Decision**: Public review API responses use `Cache-Control: no-store`,
`Pragma: no-cache`, `Referrer-Policy: no-referrer`, and
`X-Robots-Tag: noindex, nofollow`. The client shell adds a `no-referrer` meta
policy, uses no external assets, analytics, or public-page links, and renders
comment text only as React text. Production links require HTTPS.

**Rationale**: These controls reduce browser, intermediary, indexer, referrer,
and active-content leakage without adding infrastructure. HTTPS protects the
bearer credential and private schedule in transit.

**Alternatives considered**:

- Rely only on the URL fragment: rejected because public API responses also
  contain private schedule and feedback data.
- Sanitize and render HTML: rejected because plain text meets the requirement
  and React text rendering is safer and simpler.

## 6. Planner authorization boundary

**Decision**: The trusted gateway is the authorization boundary. It permits
unauthenticated access only to the public review shell and its static assets,
`/api/public/lecturer-review`, and
`/api/public/lecturer-review/feedback`. It protects the planner page entry
points and every other API path, including all issue/list/revoke/replace and
retained-feedback operations. The backend is not directly publicly reachable.
The exact path policy is captured in `contracts/gateway-boundary.md` and is a
deployment acceptance gate.

**Rationale**: FS-015 explicitly adds no planner account or role system. A
gateway path boundary preserves the existing planner-only deployment model
while making only the minimum accountless surface public. It also supplies an
enforceable, testable meaning for FR-001 without expanding into FS-016.

**Alternatives considered**:

- Add a new planner-auth dependency in FS-015: rejected as an account and role
  redesign outside the approved slice.
- Expose management actions through the bearer route: rejected because the
  bearer grants read and feedback only.
- Rely on hidden planner UI controls while leaving management APIs public:
  rejected because authorization must protect every read and action.

## 7. FS-013 projection and lifecycle coupling

**Decision**: Reuse FS-013 revision content semantics:

- Draft and Ready for review use the current live semester sessions.
- Current Published uses its captured revision snapshot.
- Abandoned and superseded revisions are unusable.

Publishing the bound revision for the first time leaves its link active.
Abandonment and supersession terminalize active links atomically inside the
existing lifecycle transaction. Restoring an abandoned revision does not
reactivate those links.

**Rationale**: FS-013 already defines what a revision contains. Explicit
terminalization is required because an abandoned revision can later be restored
with the same ID; checking current state alone could otherwise revive ended
credentials.

**Alternatives considered**:

- Copy the complete lecturer schedule into the link at issuance: rejected
  because the spec requires current assignment changes and an empty/repopulated
  review to appear automatically.
- Validate only on initial page load: rejected because every protected view and
  feedback submission must recheck validity and current scope.
- Revoke on publication: rejected because publication is expressly not a link
  end condition.

## 8. Course identity

**Decision**: Use the existing stable course source ID and the same derived
display code pattern already used by the calendar workspace:
`COURSE-{sourceCourseId}`. Store and return the course name alongside it.

**Rationale**: `Course` has no institution-assigned code field. The derived
code is stable for the retained revision and does not require an academic
catalog migration.

**Alternatives considered**:

- Add a new course reference-code field: rejected because it changes academic
  data entry, validation, imports, and existing screens beyond this slice.
- Omit all stable course identity: rejected because name alone may be ambiguous
  and FR-025 asks for title and code.

## 9. Link, feedback, and activity persistence

**Decision**: Add three durable entities:

1. `LecturerReviewLink` for digest, scope, expiry, status, replacement chain,
   and valid-link throttle state.
2. `LecturerReviewFeedback` for immutable advisory items, a current
   submission-time session snapshot, and a client submission ID.
3. `LecturerReviewActivityEvent` for typed, privacy-safe evidence required by
   FR-058.

Use a partial unique index for one active link per revision/lecturer pair and a
unique `(link_id, client_submission_id)` constraint for retry idempotency.

**Rationale**: The records have different lifetimes and disclosure rules.
Separating them prevents raw comments from entering security evidence and lets
ended credentials coexist with retained planner feedback.

**Alternatives considered**:

- Put feedback and activity into the link row as JSON arrays: rejected because
  immutable append semantics, grouping, counts, uniqueness, and concurrency
  would become harder.
- Reuse `ScheduleRevisionEvent`: rejected because lecturer access/feedback
  activity has different privacy fields and much higher request volume than
  lifecycle transitions.
- Add a generic audit subsystem: rejected because only this feature's typed
  evidence is currently required.

## 10. Feedback identity and stale-session behavior

**Decision**: Feedback attribution reads “submitted through the link intended
for {lecturer name},” never “submitted by authenticated lecturer.” Each
session-specific item stores `session_kind`, source session ID, and the
minimum permitted session context as it exists when the submission is accepted.
The server revalidates current assignment scope immediately before insertion;
an in-scope edit is accepted without confirmation and an out-of-scope session
is rejected.

The browser sends one UUID `clientSubmissionId` for a logical attempt and
retains it across an ambiguous retry. Reusing the ID with the same canonical
request returns the original item; reusing it with different content returns a
conflict. A deliberate additional item uses a new UUID.

**Rationale**: This implements the clarified current-state rule, preserves
historical meaning after edits, and prevents network retries from duplicating a
submission without merging deliberate repeated flags.

**Alternatives considered**:

- Optimistic session-version confirmation: rejected by the clarification that
  current in-scope state is authoritative without a stale warning.
- Editable comments or one mutable flag per session: rejected because feedback
  is immutable and every successful deliberate submission is separate.

## 11. Concurrency boundary

**Decision**: Follow the existing lifecycle claim/revalidate pattern. Mutations
claim the bound semester, then the link when present, reload authoritative
state, and commit the state change plus evidence together. Initial issuance
also relies on the partial unique active-pair index. Feedback serializes against
reassignment, abandonment, supersession, revoke, and replace at the same
semester boundary.

**Rationale**: The repository already uses a no-op semester update, database
constraints, explicit commit/rollback, and file-backed SQLite concurrency
tests. The operation that acquires the authoritative boundary first wins;
waiting operations reload and either proceed or fail closed.

**Alternatives considered**:

- Process-only locks: rejected because they do not coordinate independent
  database sessions and would not match existing lifecycle behavior.
- Distributed locking: rejected because current storage and deployment do not
  require it.

## 12. Misuse controls

**Decision**:

- Unusable links: an atomic, database-backed short-lived source-limit record
  keyed by
  `HMAC-SHA256(configured-stable-secret, request.client.host)` records no raw
  address. `request.client.host` is authoritative only after the trusted
  gateway overwrites forwarding values and Uvicorn accepts proxy headers solely
  from the configured gateway address. Each record contains only bounded
  rolling-five-minute attempt timestamps, optional `blocked_until`, and
  `last_relevant_at`. Attempts after 20 in five minutes receive the same generic
  unavailable response for at least ten minutes. A one-minute cleanup task
  physically removes records no later than 15 minutes after their last relevant
  attempt. The configured secret contains at least 256 bits of random key
  material and remains stable across application restarts; production startup
  fails when it is missing or shorter.
- Valid protected views: derive the rolling five-minute count from typed link
  activity and set a five-minute `access_blocked_until` when request 121
  arrives.
- Valid feedback: derive the one-minute and one-hour counts from typed link
  activity. Request 11 or 61 is rejected until both rolling counts fall below
  their limits.

All clocks are injected for boundary tests. The gateway discards or overwrites
caller-provided `Forwarded` and `X-Forwarded-*` values, writes the authoritative
client address, and is the only permitted backend peer. Uvicorn proxy-header
trust is restricted to that gateway address through
`--proxy-headers --forwarded-allow-ips=<gateway-peer-or-CIDR>` or the equivalent
`FORWARDED_ALLOW_IPS` setting and must never use a wildcard.

**Rationale**: The hybrid uses durable typed events already required for known
links and adds one short-lived database record for sources that have no safe
domain identity. The existing database provides restart-safe, atomic
enforcement without adding Redis, another service, raw network identifiers, or
a third-party limiting library.

**Alternatives considered**:

- Persist raw or plain-hashed IP addresses: rejected by data-minimization and
  retention requirements.
- Parse or trust forwarding headers inside the FastAPI feature code: rejected
  because header sanitation and peer trust belong at the gateway/Uvicorn
  boundary and are unsafe when duplicated in application logic.
- Use only the direct TCP peer without trusted proxy handling: rejected because
  every reviewer would share the gateway's address and one source could block
  all reviewers.
- Add Redis or another distributed limiter: rejected because there is no
  existing cache service and the existing database satisfies this slice.
- Use only process memory: rejected because an application restart would
  discard attempts and shorten an active rejection period, violating FR-054.
- Count only successful submissions: rejected because the requirement limits
  submission attempts and malformed floods must not bypass protection.

## 13. Planner Lecturer coordination destination

**Decision**: Rename the implemented Schedule destination to **Lecturer
coordination** and keep link management with retained feedback. Filter
individual immutable items by intended lecturer, course, session kind, and
feedback kind before regrouping. Recompute all feedback, comment,
impossible-item, and distinct-affected-session counters from the same active
set. Use the existing guarded Schedule navigation for current occurrences.

**Rationale**: The implemented destination already owns link lifecycle and
feedback handling. Broadening that surface avoids a second dashboard or generic
Action Center, while item-first filtering handles mixed historical groups
without changing stored feedback.

**Alternatives considered**:

- Keep only the original impossible filter: rejected because planners need
  course, lecturer, session-kind, and feedback-kind coordination in this slice.
- Add server-side cross-revision search: rejected because the selected Schedule
  revision is already fixed context and the current overview is complete for
  that scope.
- Modify the schedule automatically from feedback: rejected because every item
  remains advisory.

## 14. Public route isolation with shared restricted presentation

**Decision**: Preserve exact-path bootstrap and the dedicated safe public DTO,
then normalize that DTO to an access-neutral schedule presentation model.
`LecturerReviewPage` composes the established calendar, neutral list, filters,
session pane, and discard dialog through an explicit lecturer-review access
profile. Shared presentation chunks may load; the planner `App`, planner API
adapters, broader planner DTO, navigation, summaries, and mutation callbacks
may not.

**Rationale**: Minimum-scope transport and component reuse address different
boundaries. A safe public DTO prevents fetch-and-hide disclosure, while an
explicit restricted composition gives the lecturer the familiar FS-014/FS-019
experience without a parallel calendar/list implementation.

**Alternatives considered**:

- Return the planner calendar DTO and hide fields in the client: rejected
  because transport would expose other lecturers, resources, findings, and
  planner-only context.
- Keep the implemented flat lecturer list: rejected because mandatory
  calendar/list and session-pane reuse is the outcome of this extension.
- Duplicate lecturer-specific calendar/list components: rejected because they
  would drift from FS-014/FS-019 behavior.

## 15. Feedback completeness contract

**Decision**: Planner overview carries `feedbackAvailability` as `complete`,
`partial`, or `unavailable`. Only `complete` may provide an exact numeric flag
count or definitive zero. Partial/unavailable states use a null count and a
clear non-definitive result. The public view either returns a complete scoped
projection or fails closed; it never returns partial schedule data.

**Rationale**: This directly prevents missing data from appearing as a trusted
zero and keeps the public security boundary stricter than the planner history
display.

**Alternatives considered**:

- Infer zero from an empty array: rejected because transport/storage failures
  would be indistinguishable from a complete empty result.
- Return partial public schedules: rejected because feedback scope could not be
  authoritatively confirmed.

## 16. Agent context update

**Decision**: No agent context file is updated.

**Rationale**: This repository's `.specify/scripts` installation contains no
agent-context update script or agent context target. The plan and its
cross-stack contracts are the authoritative design context for the next Spec
Kit phases.

**Alternatives considered**:

- Invent a new context file or script: rejected because it is not part of the
  repository's configured Spec Kit workflow.

## 17. Implemented baseline versus extension persistence

**Decision**: Keep migration `0009_lecturer_token_review.py`, all four
implemented record types, lifecycle transactions, endpoints, and token
transport unchanged. The calendar/list and Lecturer coordination extension
adds no table, index, migration, persisted filter, or persisted draft.

**Rationale**: The existing link, feedback, activity, and misuse records already
represent every durable business and security fact. Workspace mode, date
anchor, filters, pane selection, and unsubmitted feedback are transient client
state.

**Alternatives considered**:

- Persist public workspace state or feedback drafts: rejected because the spec
  makes drafts transient and does not require cross-visit restoration.
- Add a new aggregate table for coordination counters: rejected because the
  reference scale is small and counts derive from immutable feedback.

## 18. Shared workspace reuse boundary

**Decision**: Reuse `CalendarPlanningWorkspace` and `SessionPane` through a
discriminated lecturer-review access profile. Extract one neutral selectable
occurrence-list renderer from the established planner List path and use it in
both access modes. Keep exact transport validation in
`api/lecturerReview.ts`; place the single public-to-presentation adapter and
filter mapping in `components/calendarWorkspaceUtils.ts`. Planner behavior
remains the default.

**Rationale**: The current public page is a parallel flat course/session list,
while the specification requires the familiar calendar/list/filter/pane
experience. An explicit access profile can remove planner-only context,
facets, fields, summaries, and actions from the DOM while retaining modes,
period navigation, selection, focus, and responsive behavior. A shared neutral
list is justified because both planner and lecturer modes now need selectable
teaching/exam occurrence rows.

**Alternatives considered**:

- Keep the current standalone public list: rejected because it contradicts
  mandatory component reuse and calendar/list parity.
- Feed `DraftSchedulePanel` fake planner values: rejected because it couples
  the public review to edit models and risks exposing planner semantics.
- Fetch the planner Calendar workspace and hide fields: rejected because hidden
  planner data would cross the public security boundary.

## 19. Restricted public workspace contract

**Decision**: Expand the existing `PublicReview`, `PublicCourse`, and
`PublicSession` DTOs with only the fields required for restricted presentation:
semester bounds, stable safe course/room references, cohort, study type,
teaching units or exam duration/type, bound lifecycle, sanitized current
validation availability/findings, and facets for course, cohort, room, study
type, session type, lifecycle, and validation. Do not expose a lecturer facet,
available revisions, planner summaries/outcomes, raw finding details, contacts,
notes, eligibility, mutation inputs, or other lecturer identities.

**Rationale**: The current public DTO cannot drive the shared calendar or pane.
A dedicated whitelist keeps the public contract smaller than the planner
Calendar DTO and lets exact-key tests remain privacy canaries.

**Alternatives considered**:

- Return the full planner `CalendarWorkspace`: rejected because it contains
  unrelated revision contexts, summaries, outcomes, and sensitive finding
  references.
- Add a second public endpoint: rejected because the current GET already owns
  the complete review projection and one atomic response avoids partial scope.

## 20. Validation derivation and sanitization

**Decision**: Refactor the existing private FS-014 derivation in
`backend/app/services/calendar_workspace.py` into one internal reusable
function, retain its planner behavior through
`backend/tests/services/test_calendar_workspace.py`, invoke it over the
complete bound revision from the lecturer-review service, then whitelist only
category, availability, safe message, and scoped occurrence association. An
out-of-scope conflict counterpart, subject reference, other lecturer, planner
note, raw configuration, and administrative capacity context never cross the
public response.

**Rationale**: Validating only scoped occurrences can falsely report no issue
when the counterpart is outside lecturer scope. Deriving complete revision
findings first preserves correctness; sanitizing afterward preserves privacy.
Legacy or incomplete validation context is partial/unavailable, never
converted to no-current-issue.

**Alternatives considered**:

- Validate only the lecturer subset: rejected because cross-scope conflicts can
  disappear.
- Send raw findings and redact in React: rejected because the public response
  itself must be minimum-scope.

## 21. Lecturer coordination filtering and counters

**Decision**: Keep the existing revision-scoped planner overview endpoint.
Within the selected Schedule revision, filter immutable feedback items
client-side by intended lecturer, course, session kind, and feedback kind,
regroup the filtered items, and recompute total items, comment items,
impossible-session items, and distinct affected sessions from that identical
active filter scope. A revision facet is not rendered when the outer Schedule
context already fixes the only revision.

Comments count `revision_comment` and `session_comment` items; optional text on
an `impossible_session` item does not change its kind. Course and session-kind
filters exclude revision-level comments because those items have no session
context. Historical filters use captured submission-time context. Partial or
unavailable feedback produces qualified, non-definitive counters rather than
zero.

**Rationale**: The current overview already contains every needed immutable
field at the reference scale. Item-first filtering is necessary because one
session group may contain different lecturers or feedback kinds. Retaining the
revision-scoped endpoint is the smallest design consistent with the selected
Schedule context.

**Alternatives considered**:

- Filter whole groups: rejected because nonmatching items inside a matching
  group would remain visible and counted.
- Add a cross-revision coordination endpoint: rejected for this slice because
  the main workflow and current Schedule destination are revision-scoped; it
  would expand API and navigation scope without a requirement.

## 22. Reload-only assignment projection

**Decision**: Load the assignment projection on initial open, full browser
reload, or reopening the link. Remove the current in-workspace Refresh action,
add no timer or polling, and do not re-GET the projection after successful
feedback. Append the returned accepted feedback item locally. Every feedback
POST continues to recheck current scope; a stale target is rejected with
reload/reopen guidance and no item.

**Rationale**: This is the clarified simplest behavior. The existing backend
GET is dynamic and non-cacheable, and the existing POST already performs the
authoritative current-assignment check.

**Alternatives considered**:

- Poll or push assignment changes: rejected as unnecessary complexity for an
  unlikely scenario.
- Reload after every successful feedback submission: rejected because it would
  update the visible assignment projection outside the clarified trigger.

## 23. Unsubmitted feedback protection

**Decision**: Keep session comment and impossible-explanation drafts in the
public page state keyed by occurrence. Before lecturer-initiated pane close,
session change, or a filter that would hide the target, reuse the existing
discard dialog with neutral feedback wording. Cancel preserves the draft and
context; discard clears both drafts for that target and commits the navigation.
Responsive presentation changes never prompt or clear text. Automatic scope
loss clears the target and drafts, announces why, and creates no feedback.

**Rationale**: This prevents accidental loss without creating saved drafts or a
new backend operation.

**Alternatives considered**:

- Silent discard: rejected by clarification.
- Persist one draft per session: rejected as unrelated storage and lifecycle
  scope.
- Block navigation until submission: rejected because advisory feedback must
  remain optional.

## 24. Lecturer bearer denial on planner APIs

**Decision**: Add one centralized backend request guard that parses only the
exact FS-015 bearer grammar (`Bearer` plus 43 URL-safe characters), hashes that
candidate, and rejects it on every non-public `/api/**` route only when the
digest resolves to any stored lecturer-review link, including an ended link.
The guard runs before route validation or service execution. An unrelated
bearer with the same length but no stored digest match is not classified as a
lecturer credential; it and requests without a lecturer credential continue
to rely on the trusted gateway as the planner authorization boundary. The
public allowlist and public operations remain unchanged.

**Rationale**: The current UI and gateway hide/protect planner operations, but
planner FastAPI routes do not inspect the `Authorization` header. A constructed
lecturer-link request could therefore reach a planner operation if it reached
the backend. Central rejection closes FR-079 without adding planner accounts or
dependencies to every route.

**Alternatives considered**:

- Add a dependency to every planner endpoint: rejected as broad, repetitive,
  and easy to miss.
- Treat the gateway alone as sufficient: rejected because the clarified spec
  explicitly requires backend denial of lecturer-link requests.
- Reject every 43-character bearer without resolving its digest: rejected
  because the external gateway's planner credential forwarding is outside this
  slice and an unrelated planner bearer must not be misclassified.
- Introduce application planner authentication: rejected as FS-016 scope.
